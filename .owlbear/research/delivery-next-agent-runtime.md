# Delivery-next Agent Runtime: SDK Sessions Versus VS Code Chat

> **Owning task:** none — runtime review for the Delivery-next rebuild
> **Date:** 2026-10-11
> **Question:** Delivery-next runs planner, builder, reviewer and challenger as Copilot SDK sessions
> outside VS Code. Which tools and settings does that route lose compared with VS Code chat, and is
> any other route feasible?

## 1. Context and Question

Delivery-next (`owlbear-dev-next/serve/delivery-next/`) runs each step as a Copilot SDK session. The
runtime is the installed Copilot CLI 1.0.95 over stdio. This is route "R2+3" in
[delivery-next-route-comparison.md](delivery-next-route-comparison.md) (L1). That recommendation is
`autonomous`; the user never decided it.

The user objects that the route loses VS Code features. The main example is the integrated browser
with viewports. The user fears that Delivery-next would have to re-implement VS Code functions. The
user works alone on macOS with VS Code 1.141 stable and a Copilot Business seat.

Questions answered here:

1. Which harnesses exist in VS Code 1.141, and which tools does each get?
2. How do responsive checks compare: integrated browser versus fixed-viewport Python Playwright?
3. How are model, effort and context configured in VS Code versus the SDK?
4. How far can a host program control a VS Code chat step?
5. What does each side have that the other lacks?
6. Which routes are feasible, and at what cost?
7. Which evidence is missing, and how can it be checked cheaply?

The route choice is the user's decision. This document only supplies evidence.

Revised 2026-10-11 after an independent review (R1). The earlier categorical recommendation is
withdrawn. Agent Host evidence (W16, L-AH1 to L-AH3) and route F were added.

| E2 | Builder runs a small Playwright script by shell | Any size | Full | Very low; Playwright is already used (X6) | Agent must write and run the script well |
| F | Delivery as an AHP client of the editor host or of `code agent host`; one session and chat per step | No window tools in sessions Delivery creates (P3) | Model, approvals, cancel, steering and usage probed (P3, P8) | Python AHP client module | Protocol 0.x churn (L-AH2) |
| C+ | Route C started by `code chat` in a Copilot-harness window, then driven over AHP: Delivery cancels the window's first turn, joins with its result tool, sends each turn with model and effort | Interactive, any viewport (P6) | Model, effort, cancel, steering, usage and result probed (P6 to P8) | Python AHP client module plus workspace settings | Experimental harness setting; window tools need session auto-approve, only `sandboxEnabled` confines it (P6, P10); full lifecycle not yet shown in one run (R2) |

Route D is not the only way to give agents a viewport. Route E2 gives the same power with no new
server, because the Python Playwright dependency already exists.

Route F rests on a public protocol whose chat channel is Stable (W16). VS Code's transport is
WebSocket over a local socket with a connection token (W16, L-AH2). The 1.141 CLI cannot connect to
the editor host yet, because it offers protocol 0.9.0 and the host speaks 0.10.0 (L-AH2).

## 4. Recommendation, Confidence, And Limits

There is no categorical recommendation. The earlier one gave A and E2 almost no cost, rated B and C
without an estimate, and treated untested controls as exclusions (R1). It is withdrawn.

Deterministic Playwright gates (X6) can coexist with any route.

**Assessment (`autonomous`, confidence low to medium until the probes run):** F looks most promising
if the probes pass. It keeps Delivery's control (approvals, cancel, usage) and gains VS Code's tools.
C is the bounded fallback. A remains for headless runs.

**Update after the probes (`autonomous`, confidence medium):** F fails its decisive probe: sessions
Delivery creates get no VS Code tools (P3). That triggers TD-36 (route C). Plain route C would break
TD-32 and TD-27: the window ignores the agent file's model and may run `auto` (P7). C+ keeps TD-36's
entry point and fixes that: Delivery cancels the window's first turn before any usage and sends
each turn itself with model and effort (P7). It also gives the watcher read, steer and stop (P6,
P8), and the user reads the same chat in the window. Recommended for VS Code-tool steps and for
TD-35's "all in VS Code" mode.

Corrections from the review (R2), all accepted:

- The first-turn cancel is a cost saver, not the TD-32 guarantee. P11 showed that neither the
  message's model field nor `chat.defaultModel` is a guarantee either. The driver now judges each
  turn by the model in its billed usage, cancels a turn billed to another model, and fails closed if
  the window's first turn ran before Delivery could cancel it (`2e069ee03`).
- Delivery acts only on a session it can bind: a nonce in the `code chat` prompt, the folder and the
  agent must match. Anything ambiguous means no action, so the user's own chats are never touched.
- Each probe showed one part. The correlated run (P11) has now passed: concurrent user chat, nonce
  binding, cancel, browser plus result, steering, window reload and stop.
- The result channel is the Delivery MCP server (step relay, P12 and P13). This was recorded as an
  owner decision under TD-36, but TD-36 concerns missing tools; corrected 2026-10-12. A client tool
  over AHP also worked (P6); using it instead needs the user's decision.

**Driver status (`autonomous`):** a stdlib AHP client (`ahp.py`) and a C+ step driver
(`vscode_step.py`) exist on PR #449 with fake-host tests. A second review by Sol found the driver
unsafe for unattended use; the fixes are in `9e9071777`: model pinned before launch, acknowledged
cancels, busy and user-turn refusal, steering correlated by text, WebSocket ping and close handled.
The runner calls it when the profile's runtime is `vscode` (`profile --runtime vscode`) and the
step has no attachments; otherwise it uses the SDK. The adapter places the agent, the `.mcp.json`
relay and the model pin for the step only, and restores every file afterwards. `code chat` runs in
the worktree, so VS Code uses or opens that folder's window. Delivery's turn names the agent file by
URI once the session lists it; an unlisted agent fails the step before its turn. Live runs: P12, P13.

**C+ session settings (from D2 to D5):** session auto-approve on, `mode: autopilot`, sandbox off,
because the sandbox blocked `uv` and Python MCP servers (P11). Pull-back still takes only the
worktree's commits; nothing stops a write elsewhere on disk while the step runs (user: low risk).

Open follow-ups (`autonomous`):

- No `now` line during VS Code steps; bootstrap usage is not counted.
- The step's window stays open; the clone's `info/exclude` keeps its entries.
- Screenshot attachments still go to the SDK.
- P12 ran once; a reused warm window and a concurrent user chat were not re-run with the adapter.

For steps without VS Code tools, TD-34 allows SDK or CLI. Sessions created over AHP (F) are a
third option with the same controls, and they show in VS Code's session list (P3).

**The route choice is the user's decision.** Nothing here changes a recorded decision.
