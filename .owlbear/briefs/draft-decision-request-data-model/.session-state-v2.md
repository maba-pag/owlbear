## CRITICAL: Resolution Model Simplified (D8 — supersedes D4/D5)

The resolution model was radically simplified based on user feedback:

**Lifecycle:** `pending` → `resolved`. Binary. Filesystem location IS the state.
**Resolution payload:** `selected_option_id` (nullable) + `free_text` (nullable) + `resolved_by` + `resolved_at`

NO status enum. No approved/rejected/needs-info/done. The content IS the answer:
- Decision + option selected = structured answer
- Decision + no option + free_text = custom answer or dismissal
- Action + free_text = outcome report or rejection reason
- "Needs-info" = resolve with free_text "I need more context about X" → task unblocks → agent reads → creates new DR if needed

User reasoning: "why is approved and rejected even the options if the intent is to have the user choose between multiple options with optional free text?" and "needs info doesn't need returned, that is resolved too... dismissed is also just resolved with a negative message in free text"

Cockpit UI: select an option and/or type text, submit. One button.

## Convergences from Synthesis (D7)
- UUID4 filenames ({request_id}.md)
- Single engine writer
- Pydantic extra="forbid" + kind-discriminated validation
- Decisions ≥2 options; actions 0 options
- Confidence 0.0-1.0, independent, not sum-to-1
- At most one recommended=True
- free_text always available
- ID-tagged summary: <!-- dr:{request_id} --> for idempotency
- create_request blocks task; resolve_request conditionally unblocks (sibling check)
- Malformed files surfaced as errors
- Slug option IDs: ^[a-z0-9][a-z0-9-]{0,61}[a-z0-9]$ (max 63)
- Max 10 options, label max 120, rationale max 500
- Resolved files immutable
- Sweep as crash-recovery fallback
- No MCP resolve tool
- Resolution atomicity: rename-as-check + marker idempotency
- CORS invariant tested

## Model Shape for Brief

### Storage Format
```yaml
---
request_id: "uuid4-string"
task_id: 1558
kind: decision  # decision | action
title: "Short title"
summary: "Card-level summary"
created_at: "2026-05-23T02:07:23+02:00"
agent: "copilot"
options:  # decision-only, ≥2, max 10
  - option_id: "slug-format"
    label: "Human label"
    confidence: 0.74
    recommended: true
    rationale: "Why this option."
resolution:  # absent when pending; present when resolved
  selected_option_id: "slug-format"  # nullable
  free_text: "Optional text"  # nullable
  resolved_by: "user"
  resolved_at: "2026-05-23T02:30:00+02:00"
---

Markdown body for extended context.
```

### Engine API
- create_request(task_id, kind, title, summary, agent, options?, body?) → file + block
- resolve_request(request_id, selected_option_id?, free_text?, resolved_by) → rename + write-back + conditional unblock
- list_requests(status?, task_id?) → list
- get_request(request_id) → single

### MCP Tools
- create_request (structured agent input)
- list_requests (filter by status/task)
- show_request (full detail + resolution)
- NO resolve tool

### Cockpit API
- GET /api/requests/pending
- POST /api/requests/{id}/resolve (submit payload)
- Cockpit imports engine directly

### First Useful Step
Data model + engine + MCP tools + Cockpit API first.
THEN: Cockpit resolver UI, list rendering, agent instruction updates.

### Excluded
- Threaded conversations, multi-user routing, recurring, multi-select, rich attachments, resolved browsing
- MCP resolve tool (deferred)
- Quick-confirm mode (deferred)
- Parallel request blocking (unspecified)
