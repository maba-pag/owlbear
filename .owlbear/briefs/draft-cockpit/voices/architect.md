# Architect Stance — Cockpit v1

**Panelist:** Architect
**Critic cycles:** 3 (exited: "position is solid")
**Date:** 2026-04-17

---

## 1. Backend Approach

**Recommendation: FastAPI + static SPA at `serve/cockpit/`** — Confidence: 95%

The cockpit backend is a new workspace package (`serve/cockpit/`) that imports `owlbear_kanban` directly — no IPC, no serialization layer beyond JSON. FastAPI serves both the HTTP API and the built SPA static files from a single process on a single port.

**Why not the alternatives:**

| Alternative | Rejection reason |
|---|---|
| VS Code webview | Couples cockpit lifecycle to VS Code. Can't demo without the IDE open. Extension packaging friction. |
| Tauri | Adds Rust toolchain dependency for zero benefit on a localhost-only single-user tool. 80-150 MB idle vs 40-80 MB for FastAPI. |
| Electron | 150-250 MB idle. Binary packaging. Overkill. |
| Static + MCP relay | MCP transport is stdio-native; bridging to HTTP adds an awkward middleware layer with no benefit over direct engine import. |

FastAPI is the only option that: (a) imports the engine in-process, (b) uses the existing `uv` toolchain, (c) serves both API and static files from one process, (d) starts with a single `uv run` command.

## 2. Frontend Stack

**Recommendation: React 19 + Vite + Porsche Design System React wrapper** — Confidence: 85%

React is chosen for ecosystem breadth, not for PDS compatibility. The cockpit needs: kanban board layout (dnd-kit), virtualized column lists at 200+ tasks (react-window or TanStack Virtual), markdown rendering (react-markdown + remark-gfm), and a mature data-fetching layer (TanStack Query). React has proven, maintained libraries for all four. SvelteKit and Vue 3 have equivalents but with thinner ecosystems for this exact combination.

**Porsche Design System** provides the design token layer, typography, and base components (buttons, dialogs, tabs, icons). Its React wrapper is officially supported and production-grade. Task cards will likely need custom components built on PDS tokens rather than using PDS components directly — PDS card components are too rigid for the indicator density required (status, priority, block state, claim state on a single card).

**Fallback:** If PDS React integration proves heavier than expected during prototyping, switch to **Radix UI primitives + Tailwind CSS** using PDS's published design tokens for color/spacing/type. This preserves the visual language while dropping the component dependency.

**Data layer:** TanStack Query for polling (3s `refetchInterval`), cache management, and optimistic mutations. It handles the exact pattern the cockpit needs — polling + mutations + rollback — in ~12KB gzipped.

## 3. Engine Adapter Shape

**Recommendation: Direct import with allowlisted HTTP surface + mtime-scan cache** — Confidence: 90%

### Package structure

```
serve/cockpit/
  pyproject.toml              # depends on owlbear-kanban, fastapi, uvicorn
  frontend/                   # React source (dev branch only)
    package.json
    vite.config.ts
    src/
  src/owlbear_cockpit/
    __init__.py
    app.py                    # FastAPI app, mounts routers + static
    routers/
      kanban.py               # kanban HTTP routes
    static/                   # built SPA (generated by CI, gitignored on dev)
```

### Exposed HTTP surface

| Method | Path | Engine call | Purpose |
|--------|------|-------------|---------|
| GET | `/api/kanban/config` | `board_config()` | Statuses, priorities, display order, claim timeout |
| GET | `/api/kanban/tasks` | `list_tasks(**filters)` | Full task list with computed `claim_status` |
| GET | `/api/kanban/tasks/{id}` | `show_task(id)` | Full task with body for detail view |
| PATCH | `/api/kanban/tasks/{id}` | `edit_task(id, **fields)` | Allowlisted fields only (title, body, priority, tags, blocked, block_reason, depends_on, parent) |
| POST | `/api/kanban/tasks/{id}/move` | `move_task(id, status)` | Status transition |
| POST | `/api/kanban/tasks/{id}/release` | `release_task(id)` | Unclaim (the one agent verb humans may invoke) |

**NOT exposed:** `create_task`, `claim_task`, `start_work`, `end_work`, `pick_dispatchable`, `sweep`. These are agent-only operations per D4.

### Cross-process visibility

The `revision` counter is **per-instance** — the cockpit's `KanbanEngine` sees only its own mutations. Agent MCP servers run in separate processes with their own engine instances.

**v1 solution:** The cockpit backend maintains a response cache invalidated by filesystem scanning:
1. On each poll request, `os.scandir()` the tasks directory → collect `{filename: mtime_ns}` dict (~1ms for 200 files).
2. If scan matches the cached scan → return cached JSON (zero engine calls).
3. If any file mtime differs → call `list_tasks()`, rebuild cache, return fresh data.

This is correct because `os.replace()` (the engine's atomic-write primitive) reliably updates the target file's mtime. The expensive path (full YAML parse of 200 files) only runs when files actually changed. The cheap path is ~1ms.

### Computed fields

The API response enriches `TaskSummary` with:
- `claim_status`: `"running"` | `"stuck"` | `"free"` — computed server-side from `claimed_by`, `claimed_at`, and `board_config().claim_timeout`. The frontend never parses durations or compares timestamps.

## 4. Extensibility Contract

**Recommendation: Static registry + typed surface interface + CSS Grid shell** — Confidence: 85%

### Shell layout (CSS Grid)

```
┌─────────┬──────────────────────────┬──────────┐
│         │                          │          │
│   nav   │       workspace          │ sidecar  │
│         │                          │ (reserved│
│         │                          │  empty)  │
├─────────┤                          │          │
│contextual                          │          │
│(reserved│                          │          │
│  empty) │                          │          │
├─────────┴──────────────────────────┴──────────┤
│                  status                        │
└────────────────────────────────────────────────┘
```

Five grid areas. `contextual` and `sidecar` render empty in v1 but their grid tracks exist, so future surfaces claim them without shell rework.

### Surface interface

```typescript
interface CockpitSurface {
  id: string;           // unique key, e.g. "kanban"
  label: string;        // nav display text
  icon: string;         // DS icon identifier
  route: string;        // URL path segment, e.g. "/kanban"
  component: React.ComponentType;
  statusSources?: StatusSource[];  // health indicators for status region
}

interface StatusSource {
  id: string;
  label: string;
  poll: () => Promise<HealthStatus>;  // green | yellow | red
}
```

### Surface registration

Static array in a single registry file. Adding a surface = one file + one import + one array entry:

```typescript
// surfaces/index.ts
import { kanbanSurface } from "./kanban";
// future: import { decisionQueueSurface } from "./decision-queue";

export const surfaces: CockpitSurface[] = [
  kanbanSurface,
];
```

No dynamic plugin system. 8 planned surfaces on a single-user laptop do not justify runtime plugin loading. YAGNI.

### Data-fetching pattern

Each surface manages its own data lifecycle via TanStack Query hooks. The shell provides:
- Base API URL via React context
- Status region subscription (surfaces register `StatusSource` instances)
- Router outlet (renders active surface's component)

Surfaces own their queries, mutations, and polling intervals. The shell owns navigation, layout, and status aggregation.

### Backend extensibility

Future surfaces add FastAPI router modules within `serve/cockpit/src/owlbear_cockpit/routers/`. Each router imports its own engine package. The cockpit's `pyproject.toml` adds dependencies as surfaces land:

```python
app.include_router(kanban_router, prefix="/api/kanban")
# future: app.include_router(knowledge_router, prefix="/api/knowledge")
```

One process, one port, growing dependency list.

## 5. Packaging and Distribution

**Recommendation: Frontend source on dev only; CI builds assets into main** — Confidence: 80%

| Artifact | Dev branch | Main branch |
|----------|-----------|-------------|
| `serve/cockpit/frontend/` (React source) | ✓ Present | ✗ Excluded from sync |
| `serve/cockpit/src/owlbear_cockpit/static/` (built SPA) | ✗ Gitignored | ✓ Injected by CI |
| `serve/cockpit/src/owlbear_cockpit/` (Python backend) | ✓ Present | ✓ Synced |
| `serve/cockpit/pyproject.toml` | ✓ Present | ✓ Synced |

**Dev workflow:** Vite dev server (port 5173) + FastAPI (port 8000) running concurrently. FastAPI proxies `/` to Vite in dev mode for hot-reload. `uv run cockpit --dev` starts both.

**Consumer workflow (main branch):** `uv run cockpit` serves pre-built static files from `static/`. No Node.js required. "Clone = install" preserved.

**CI change:** The `sync-to-main` GitHub Actions workflow gains a build step: `cd serve/cockpit/frontend && npm ci && npm run build` → output to `../src/owlbear_cockpit/static/` → include in main commit.

## 6. Single Highest-Risk Assumption

**Risk: Full task-list reload cost at scale is unknown.**

The cockpit polls the engine every 3s. With the mtime-scan cache, the expensive path (200 YAML parses + Pydantic validation) only fires when files changed. But we don't know the actual latency of that expensive path. If it's >300ms, the UX may stutter during busy agent activity (many concurrent writes).

**Validation plan:**
1. **Before locking the architecture:** Write a benchmark script that creates 200 synthetic tasks and measures `list_tasks()` latency. Target: <150ms p99.
2. **If it exceeds 150ms:** Add a filesystem watcher (FSEvents on macOS via `watchfiles`) that triggers background cache refresh, so the poll endpoint always returns from cache. The watcher approach is ~30 lines of code and eliminates poll-triggered latency entirely.
3. **If the watcher approach proves unreliable:** Add a shared revision file (`.owlbear/kanban/.revision`) that all engine instances increment on write. This requires a small `owlbear_kanban` change but provides O(1) change detection.

This is the assumption most likely to force early rework. Validate in the first sprint.

## Key Trade-offs

| Decision | Gains | Costs |
|----------|-------|-------|
| FastAPI in-process import | Zero IPC overhead, single `uv run`, full engine access | Cockpit process holds engine file locks during writes; agent contention possible (mitigated by engine's `fcntl.flock`) |
| React over SvelteKit | Richest ecosystem for exact needs (dnd, virtual lists, markdown) | Larger bundle (~100KB gz vs ~40KB), more boilerplate than Svelte |
| Always-poll over SSE/WebSocket | Simple, stateless, no connection management | 2-5s staleness; wasted polls when nothing changed (mitigated by mtime-scan cache) |
| Static surface registry | Zero runtime complexity, explicit dependency graph | Adding a surface requires rebuild; acceptable for 8 planned surfaces |
| CI-built assets | Clean git history on dev, no Node.js for consumers | Adds CI build step; dev requires local Node.js + Vite |

## Warnings

1. **Porsche DS card rigidity.** PDS components may not support the indicator density needed for task cards (status + priority + block + claim state). Budget time for a card prototype early. If PDS cards are too rigid, custom cards on PDS tokens are the fallback — not a different DS.
2. **Frontend source exclusion from main.** Consumers cannot modify the frontend without switching to the dev branch. This is intentional (consumers are operators, not developers) but must be documented.
3. **Single-process coupling.** The cockpit backend and engine share a process. A bug in the cockpit server could theoretically corrupt task files via the engine. Mitigated by: engine's own file locking, git as safety net, and the fact that the cockpit only calls safe engine methods.

**Overall confidence: 88%.** The 12% uncertainty is concentrated in PDS card flexibility (validate with prototype) and list-tasks-at-scale latency (validate with benchmark).
