# Architect — Critic Debate Log

## Cycle 1

### Architect Position (Initial)

1. **Backend:** FastAPI + static SPA at `serve/cockpit/`. Import `owlbear_kanban` directly. Single process, single port.
2. **Frontend:** React + Vite + Porsche DS React wrapper. Fallback: Radix UI + Tailwind if PDS cards too rigid.
3. **Engine adapter:** HTTP routes expose allowlisted surface only. Use per-instance `revision` for frontend change detection. Cross-process visibility via directory mtime polling.
4. **Extensibility:** Route-based surfaces, typed `CockpitSurface` interface, CSS Grid shell with reserved slots, static registry.
5. **Packaging:** Commit built SPA assets to dev; sync-to-main copies them.
6. **Highest risk:** Revision counter is instance-scoped — cockpit blind to agent mutations via MCP.

### Critic Challenge (C1)

> **C1-1.** "Directory mtime doesn't change when a file's *contents* change — only when files are added or removed. `edit_task()` modifies file contents in-place via `os.replace` (atomic rename of temp file). On macOS APFS, `os.replace` into an existing path *does* update the parent directory's mtime because the directory entry is updated. But on some filesystems it doesn't. Your cross-process detection is filesystem-behavior-dependent. What's your fallback?"

> **C1-2.** "You say 'commit built assets to dev.' React build output is hundreds of content-hashed files. Every rebuild changes every filename. Git history becomes noise. Diffs are unreadable. Is this acceptable for Shared tier?"

> **C1-3.** "Your extensibility contract defines a TypeScript interface but doesn't explain how future surfaces with *different* backend engines (knowledge search imports `owlbear_knowledge`, not `owlbear_kanban`) register their routes. Does every surface couple to the cockpit backend?"

### Architect Response (C1)

**C1-1 — Accepted. Revised cross-process detection strategy.**

Drop the mtime-based approach. Instead: the cockpit backend always calls `list_tasks()` from disk on each poll — the engine is filesystem-backed with no in-memory cache. Every `list_tasks()` reads current task files. The "revision" endpoint returns a hash of the serialized task list. If the hash differs from the frontend's last-known hash, the frontend fetches fresh data.

Performance concern at 200 tasks: add a lightweight cache in the cockpit backend. On each poll, `os.scandir()` the tasks directory (~1ms for 200 entries), compare file mtimes against cached values. If any file changed, reload from engine; otherwise return cached response. This is correct because `os.replace()` (used by the engine for atomic writes) *does* reliably update the replaced file's mtime.

**Simplest v1 path:** Just poll the full task list every 3s. At 200 tasks over localhost, the JSON payload is ~50-100KB and the response time is <100ms. Optimize with caching only if profiling shows otherwise.

**C1-2 — Accepted. Revised packaging.**

Don't commit built assets to dev. Instead:
- Frontend source lives in `serve/cockpit/frontend/` (dev branch only, excluded from main sync).
- Built assets are generated by the `sync-to-main` GitHub Actions workflow: `npm ci && npm run build` → output to `serve/cockpit/src/owlbear_cockpit/static/` → committed to main.
- Dev workflow: Vite dev server on port 5173 alongside FastAPI on port 8000. FastAPI proxies `/` to Vite in dev mode.
- Consumer (main branch): pre-built assets served by FastAPI directly. "Clone = install" preserved for consumers.

**C1-3 — Accepted. Clarified multi-engine pattern.**

The cockpit backend is the single HTTP process. Future surfaces add FastAPI router modules *within* `serve/cockpit/`. Each router imports its own engine package. The cockpit's `pyproject.toml` adds dependencies as surfaces land:

```python
# app.py
app.include_router(kanban_router, prefix="/api/kanban")
# future: app.include_router(knowledge_router, prefix="/api/knowledge")
```

One server, one port, growing dependency list. Frontend mirrors this: each surface has its own API client module sharing the base URL.

## Cycle 2

### Architect Position (Revised)

Incorporated all C1 changes: always-poll-from-disk for v1, CI-built assets, multi-router backend pattern.

### Critic Challenge (C2)

> **C2-1.** "You say 'always poll the full task list at 3s' and 'the engine reads from disk every time.' But `list_tasks()` reads and parses 200 YAML files, validates through Pydantic, serializes to JSON. Have you estimated the actual latency? If it's 300ms per poll, you're burning 10% of a CPU core on polling alone."

> **C2-2.** "TanStack Query is mentioned for data fetching but you have 6 mutations and one primary query. Is the abstraction justified for v1, or is it premature complexity?"

> **C2-3.** "The activity panel derives running/stuck/free from claim fields + `claim_timeout`. But `claim_timeout` is a string like '1h' in `BoardConfig`. Who parses the duration — the backend or the frontend? And what about clock skew between the agent process and the cockpit process?"

### Architect Response (C2)

**C2-1 — Partially accepted. Added caching recommendation.**

The always-poll approach is the *starting* position for v1 simplicity. But the Critic is right that 200 YAML parses could be costly. Mitigation: the cockpit backend maintains a response cache keyed on a scan of file mtimes. Each poll:
1. `os.scandir()` tasks dir → collect `{filename: mtime_ns}` (~1ms)
2. If scan matches cached scan → return cached JSON response (zero engine calls)
3. If scan differs → call `list_tasks()`, cache response + scan, return fresh data

This means the expensive path only runs when files actually changed. The cheap path (no changes) is ~1ms. This is worth building in v1 because it's ~20 lines of code and eliminates the performance uncertainty.

**C2-2 — Rejected. TanStack Query justified.**

TanStack Query handles polling interval, background refetch, cache invalidation, optimistic mutations, error/loading states, and stale-while-revalidate — all of which the cockpit needs. Reimplementing this with raw `useState`/`useEffect` for 6 mutations + 1 query + 1 poll would be more code, not less. The library is 12KB gzipped. It's the right abstraction.

**C2-3 — Accepted. Clarified claim computation.**

`claim_timeout` parsing happens in the **backend**. The cockpit API response includes a computed `claim_status` field per task: `"running"`, `"stuck"`, or `"free"`. The frontend never parses duration strings or compares timestamps.

Clock skew: irrelevant. Both the agent and the cockpit run on the same laptop. `claimed_at` is written by the agent's process; the cockpit reads it and compares against its own `datetime.now()`. Same system clock. No skew.

## Cycle 3

### Architect Position (Hardened)

All six topics refined through two cycles. Caching strategy added, packaging clarified, multi-engine pattern documented, claim computation assigned to backend.

### Critic Challenge (C3)

> **C3-1.** "The context says 'Tech first, design second' for DS selection, but your React recommendation cites PDS React wrapper availability as a factor. Are you choosing React because of PDS, or PDS because of React? Circular reasoning?"

> **C3-2.** "Your extensibility contract reserves CSS Grid slots for future layout regions (contextual nav, sidecar). But CSS Grid areas must be defined at the shell level. If a future surface needs a layout region the shell didn't anticipate, you're back to shell rework. How specific should the reserved regions be?"

> **C3-3.** "You recommend a static surface registry — adding a surface requires a code change + rebuild. The context lists 8 future surfaces. Won't this become friction?"

### Architect Response (C3)

**C3-1 — Rejected.**

React was chosen for ecosystem breadth: kanban/dashboard patterns, virtualized lists, react-markdown, dnd-kit, testing-library. PDS wrapper availability is confirming evidence, not the driver. If PDS had no React wrapper, I'd still choose React and use PDS Web Components (which work in any framework) or Radix UI. The reasoning is not circular.

**C3-2 — Partially accepted. Refined slot definition.**

The shell defines 5 grid areas: `nav`, `workspace`, `status`, `contextual` (reserved), `sidecar` (reserved). Reserved areas render empty but their grid tracks exist. A future surface that needs a region *not* in this set would modify the shell's grid template — a one-line CSS change, not a rework. The shell's job is to own the outer grid; surfaces own their internal layout. This is the right boundary.

Caveat: I will NOT over-specify the reserved regions. Two reserved slots is enough. If a future surface needs something radically different (e.g., a full-bleed canvas), it can replace the workspace area's internal layout without touching the shell grid.

**C3-3 — Rejected. Static registry is correct.**

Each of the 8 future surfaces is a separate Brief with its own implementation work. Adding a surface means adding a file, an import, and a registry entry — three lines of code. This is not friction; this is the minimum viable contract. A dynamic plugin system for 8 planned surfaces on a single-user laptop is textbook YAGNI.

### Critic Assessment

Position is solid. The cross-process detection strategy, packaging split, and extensibility boundaries are well-reasoned. The mtime-scan cache is a pragmatic addition. No remaining material flaws.
